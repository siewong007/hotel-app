# v0.2.0 Release Design

## Goal

Publish `v0.2.0` from `master`, deploy that exact release to production, and provide the macOS desktop build produced by the existing tag workflow.

## Version Scope

- Set `hotel-app-be` to `0.2.0` in its Cargo manifest and lockfile.
- Set `hotel-web-fe` to `0.2.0` in its package manifest. Its Bun lockfile does not store the root package version and must remain dependency-equivalent.
- Keep `hotel-desktop` at `1.0.0`; changing it to `0.2.0` would be a version downgrade.
- Use the repository-wide Git tag `v0.2.0`.

## Release Flow

1. Update only the backend and web version metadata.
2. Run the repository's backend, frontend, and desktop release checks.
3. Commit the version update to `master` and push it.
4. Wait for the push CI workflow and its production deployment workflow to succeed.
5. Verify the public frontend and health endpoint are serving successfully.
6. Create and push the annotated `v0.2.0` tag at the verified release commit.
7. Wait for the tag-triggered macOS desktop workflow to succeed.
8. Create the GitHub Release with generated notes covering changes since `v0.1.0`.
9. Download the desktop workflow artifact, package it with an unambiguous platform/version filename, and attach it to the GitHub Release.

The release commit is the source of truth for the tag, production deployment, release notes, and desktop artifact.

## Verification Gates

Backend:

```bash
cargo fmt --check
cargo check --all-features
cargo clippy --all-features -- -D warnings
cargo test --all-features
```

Frontend:

```bash
bun install --frozen-lockfile
npx tsc --noEmit
npm run build
```

Desktop:

```bash
bun install --frozen-lockfile
cd src-tauri
cargo fmt --check
cargo check
```

The existing GitHub Actions CI, production deployment health checks, and tag-triggered desktop build remain authoritative remote gates.

## Failure Handling

- Do not create the tag if local checks, CI, production deployment, or public health verification fails.
- If the desktop build fails after the tag is pushed, keep the tag fixed, correct the build on `master`, and explicitly decide whether a patch release is required rather than moving the published tag silently.
- Do not publish the GitHub Release until the desktop workflow succeeds and its artifact is available.
- Rely on the existing deployment workflow's backup, health-check, and rollback behavior for production failures.

## Non-Goals

- No new release automation or dependencies.
- No desktop version downgrade.
- No application behavior, API, schema, or infrastructure changes.
- No rewriting or moving the existing `v0.1.0` tag or release.
