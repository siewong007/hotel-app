# i18n Consolidation + Simplified Chinese — Design

**Status:** approved direction (user answered scoping questions 2026-09-14)
**Scope:** hotel-web-fe + hotel-app-be + database patch. No desktop-specific work
beyond what the shared frontend/backend already produces.

## Decisions (from user)

| Question | Decision |
|---|---|
| zh locale code | `zh` stored code, `intlTag: 'zh-CN'` (existing bare-subtag convention) |
| Execution | Full sweep — all domains, wave-by-wave, no pausing between waves |
| API errors | Add backend `code` fields first, then FE code→key mapper |
| Malay (`ms`) | Preserved; new keys need ms translations too (parity test requires it) |
| Legal documents | Add zh translations, flagged for human legal review |
| Docs | `docs/superpowers/plans/` for plan; `docs/guides/` for guide + glossary |

## Current architecture (audited 2026-09-14)

Custom i18n engine, i18next-shaped API. Keep it — no new dependencies.

- `src/i18n/locales.ts` — registry; `code` = bare ISO-639-1 (`en`, `ms`),
  `intlTag` = BCP-47. `matchLocale` matches on primary subtag.
- `src/i18n/translator.ts` — pure engine: `ns:key` lookup, `{{var}}`
  interpolation (same syntax as backend email templates), plural suffixes via
  `Intl.PluralRules` (`_zero` optional, `_other` mandatory).
- `src/i18n/localeStore.ts` — module store + `useSyncExternalStore`.
  Precedence: explicit choice (localStorage `locale`) > `applyDefaultLocale`
  (hotel `default_locale` setting / guest `language_preference`) >
  `navigator.languages` > `en`.
- `src/i18n/translate.ts` — `t` (non-React), `translateFor`, `translateOr`
  (incremental-migration door: renders fallback when key absent), dev-mode
  missing-key warnings.
- `src/i18n/useTranslation.ts` — `useTranslation(ns)` → `{t, tOr, locale, dir,
  setLocale}`; every subscriber re-renders on switch.
- `src/i18n/I18nProvider.tsx` — mirrors `lang`/`dir` onto `<html>`.
- `src/i18n/format.ts` — memoized `Intl` formatters; dates render in interface
  language; currency deliberately pinned to currency-code formatting.
- `LanguageSwitcher` — one component (icon + list variants), mounted in
  `AppTopbar`, `LoginPage`, `RegisterPage`, `GuestPortalShell`.
- `navigation/routeLabels.ts` — `useRouteLabels` maps route ids → `nav:` keys
  with registry English as `tOr` fallback.
- `utils/apiNotifications.ts` — central API-error toast plumbing
  (`getApiNotificationMessage`, `emitApiNotification`).
- Backend `core/i18n.rs` — `Locale`, `SUPPORTED_LOCALES = ["en","ms"]`,
  email catalog `core/locales/{en,ms}.json`, `format_date` with catalog month
  names, full parity test suite.
- Backend `core/error.rs` — `ApiError` → `{"error": <english>, "code": <opt>}`;
  only 3 variants carry codes today.
- `resources.test.ts` — parity, plural coverage, placeholder parity, no-blank,
  on-disk registration.

### Coverage gap

~22 of ~342 feature TSX files use `useTranslation` (help, auth, guestPortal,
legal, paymentRecovery). The entire staff app is hardcoded English:
~1,400 literal `label/placeholder/title/aria-label/helperText` props and
~1,000 JSX text nodes across ~173 files — est. 2,500–4,000 strings.

## Target design

### Locales

- Add `zh` to `LOCALES`: `intlTag 'zh-CN'`, `nativeName '简体中文'`,
  `englishName 'Chinese (Simplified)'`, `dir 'ltr'`.
- `matchLocale`/`Locale::parse` unchanged: `zh-CN`, `zh-Hans`, `zh-TW`, `zh-HK`
  all resolve to `zh` (Simplified is the closest available variant).
- `consent_records_locale_check`: baseline gains `'zh'`; live databases get
  patch `0003_consent_locale_zh.sql` (idempotent DO-block with
  `pg_get_constraintdef` guard, matching `0002` style). Registered in
  `manifest.tsv` (version 3, contiguous), `deploy/deploy.sh` (list + install
  lines), `deploy/deploy-staging.sh`, `.github/workflows/deploy.yml`,
  `deploy-staging.yml`.
- `guests.language_preference`, `default_locale` setting accept `zh` with no
  other change (parse-based, not enumerated).

### Namespaces (16)

Existing: `common`, `nav`, `auth`, `errors`, `guestPortal`, `help`.
New: `validation`, `status`, `dashboard`, `bookings`, `guests`, `rooms`,
`finance`, `revenue`, `admin`, `notifications`.

Domain mapping (feature dirs → namespace):

| Namespace | Feature dirs |
|---|---|
| `bookings` | bookings, guest-checkin routes |
| `guests` | guests, guestRelations, support, loyalty, segments |
| `rooms` | rooms, housekeeping, night-audit, onlineInventory, rates |
| `finance` | invoices, customer-ledger, paymentRecovery, complimentary, payment-approvals, reports, data-transfer(financial parts) |
| `revenue` | revenue, insights, promotions, campaigns, communications |
| `admin` | admin, rbac, audit-log, settings, data-transfer, ekyc(admin), jobs, system-health |
| `dashboard` | dashboard |
| `notifications` | notifications UI + toast vocabulary |
| `common` | shared actions/states/table chrome/pagination + misc routes (403, 423) |
| `validation` | form validation messages |
| `status` | ALL status labels, all domains |

`common` is the single home for Save/Cancel/Edit/Delete/Search/Filter/Reset/
Apply/Close/Back/Next/Confirm/Submit/Loading/No results/No data/View details/
Export/Refresh/Status/Actions/Created at/Updated at — one key each, reused
everywhere via `common:actions.save` etc.

### Status labels

New `src/i18n/statusLabel.ts`: `statusLabel(t, domain, value)` →
`t('status:<domain>.<value>')`, falling back to a humanized internal value.
Central `status` namespace holds canonical labels for every status enum:
booking, payment, invoice, room, housekeeping, maintenance task, campaign,
payroll, employee, notification. Colors/icons stay logic-driven and are not
touched.

### Backend error codes

`core/error.rs`: every `ApiError` variant emits a stable `code` in the JSON
body. Generic variant codes: `database`→`server_error`, `unauthorized`,
`forbidden`, `bad_request`, `not_found`, `conflict`, `internal`→`server_error`,
`service_unavailable`, `rate_limited`, plus the existing three
(`profile_incomplete`, `two_factor_enrollment_required`, `guest_name_taken`).
Specific business errors identified during wave work get their own codes added
to the enum as needed (e.g. `booking_conflict`, `deposit_required`) — each is a
small additive change.

FE: `apiNotifications.ts` — `getApiNotificationMessage` checks `payload.code`
first → `t('errors:api.<code>')` → falls back to server `error` text, then
status-based generic messages (which become localized `errors:status.*` keys).
`toApiError` unchanged. Uncoded server messages still surface verbatim
(current behavior) until they grow codes.

### Content

- Help articles: `articles.zh.ts` added alongside en/ms.
- Legal content: `LegalLocale` gains `'zh'`; all documents get zh translations
  **marked for legal review** (banner/comment in spec + guide, and a
  `content.test.ts`-visible note). Consent records store `locale: 'zh'` once
  the DB patch lands.

### Typography

`theme/index.ts`: `SANS_STACK` gains
`"PingFang SC","Hiragino Sans GB","Microsoft YaHei","Noto Sans SC"` after the
Latin faces; serif display option resolves to the sans stack when active
locale is zh (CJK serif display faces read poorly at UI sizes). No fixed-width
changes up front — per-page layout audit happens inside each wave and in the
final pass.

### Terminology glossary

`docs/guides/i18n-glossary.md` — canonical en↔zh(↔ms) terms for hotel-domain
concepts (预订 reservation/booking, 客人 guest, 入住 check-in, 退房 check-out,
房态 room status, 客房服务 housekeeping, 支付 payment, 退款 refund, 收入
revenue, 入住率 occupancy, 未结余额 outstanding balance, 夜审 night audit,
房价/价格计划 rate/rate plan, 促销活动 promotion, 发票 invoice, 员工
employee, 班次 shift, …). Translators and future waves consult it so one
concept = one term.

### Tests / tooling

- `resources.test.ts` automatically covers zh/ms parity, plurals, placeholders
  — no new code needed, it just has to pass.
- New `i18n/keyUsage.test.ts` (or script): scans `src/**/*.{ts,tsx}` for
  literal `t('…')`/`tOr('…')` keys and asserts each exists in the `en` bundle —
  catches typos at CI, not runtime.
- `useTranslation` tests: locale switch re-renders, persistence, fallback.
- `apiNotifications` tests: code→key mapping, fallback ordering.
- `statusLabel` tests: known value → label; unknown value → humanized fallback.
- Backend: `core::i18n` tests cover zh catalog automatically;
  `error.rs` tests assert `code` presence/shape per variant.
- Layout audit is manual per wave + a final both-languages page sweep.

## Constraints

- No new dependencies; keep the custom engine.
- Internal enums/API field names never translated; presentation-only mapping.
- `ms` stays fully key-complete (parity test).
- Never render raw `ns:key` — engine already guarantees last-segment fallback.
- Don't touch dirty-worktree files' unrelated changes (MobileNavBar, nav.json
  in-flight edits) — extend them, don't revert.
- `.worktrees/guest-relations-p2` is a concurrent session — coordinate by not
  rewriting guestRelations files' non-string logic.
- Published patch checksums immutable — `0003` is new, `0002` untouched.
- Legal zh text is marked for human legal review.

## Out of scope

- RTL languages (registry supports `dir`; no RTL locale added).
- Translating database seed content (permission names, system settings labels).
- `Accept-Language`-driven first-time guest language recording (backend hook
  exists, no handler reads it yet — unchanged).
