# i18n Consolidation + Simplified Chinese Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the entire hotel-management UI (staff app + guest portal) in English, Malay, and Simplified Chinese on the existing custom i18n engine, with localized API errors, a DB patch for consent locale, and a maintainable 16-namespace layout.

**Architecture:** Extend the existing engine — `src/i18n/` (locales registry, module store, `useTranslation`, `t`/`tOr`, `Intl` formatters), backend `core/i18n.rs` catalog, `ApiError` JSON `code` field mapped to `errors:api.*` keys. No new dependencies. Spec: `docs/superpowers/specs/2026-09-14-i18n-zh-design.md`.

**Tech Stack:** React 19 + TS strict, MUI v9, TanStack Router/Query, custom i18n, Rust/Axum/SQLx backend, PostgreSQL patch catalog.

## Global Constraints

- **No new dependencies.** The custom i18n engine stays.
- **Three locales per key:** every bundle key is authored in `en`, `ms`, AND `zh` in the same change — `src/i18n/resources.test.ts` fails otherwise (it checks parity, plural categories per `Intl.PluralRules`, placeholder parity, no blanks, on-disk registration).
- **Never render raw keys:** the engine already degrades to the last key segment; use `tOr(key, englishFallback)` for strings during migration where a fallback reads better.
- **Never translate identifiers:** internal status enums, API field names, permission names, DB values stay English; map to labels via `status:` keys.
- **Business logic stays language-neutral:** never branch on translated text.
- **zh plural rules:** Chinese has only `other` — author `*_other` (+ optional `_zero`), no `_one`. `ms` likewise has no `_one`.
- **Concurrency:** dirty-worktree files (`MobileNavBar.tsx`, `nav.json` en/ms) contain in-flight work — extend, never revert. `.worktrees/guest-relations-p2` is another session — in `features/guestRelations` change strings only, zero logic.
- **Patch immutability:** never edit a shipped patch. ⚠️ **PATCH NUMBER CHANGED —
  re-read before touching the catalog (audit 2026-09-15).** This plan was written
  when `0003` was free. Master has since shipped
  **`0003_guest_relations_phase2.sql`** (commit `c2981f1e7`), and it is already in
  `manifest.tsv` *and* mirrored into the desktop bundle, so its version and checksum
  are frozen. The `feat/i18n-zh` branch meanwhile created its own
  `0003_consent_locale_zh.sql` and registered it as **version 3** — a direct
  collision: two different files claiming generation 1 / version 3.
  **The zh patch must be renumbered to `0004_consent_locale_zh.sql`, version 4**,
  because it is the one that has not shipped. Rename the file, recompute
  `shasum -a 256`, and update the version in `manifest.tsv` plus all four deploy
  registration sites. The branch is 166 commits behind master — rebase first, then
  renumber; `postgres_patch_catalog.rs` enforces contiguity and will catch a miss.
- **Gates after EVERY task** (`hotel-web-fe/`): `bun run typecheck && bun run lint && bun run test`. Backend tasks also run `cargo check --all-features` + `cargo clippy --all-features -- -D warnings` + `cargo test --lib` in `hotel-app-be/`.
- **Commit per task** (or per coherent step group), message style: `feat(i18n): …` / `feat(be): …` matching `git log` conventions.

## Conventions for all waves

- Components: `const { t } = useTranslation('<ns>');` then `t('section.key')`, `t('common:actions.save')`, `t('status:booking.confirmed')`.
- Non-component code (utils, services, module scope): bare `t`/`translateFor` from `src/i18n` — reads locale at call time; fine for one-shot toasts, wrong for rendered text.
- Keys: `snake_case` segments (`booking.detail.checkIn`), nouns not sentences, no page-name prefixes when a shared concept exists in `common`.
- `{{var}}` interpolation; pass `count` for plurals (`_other` mandatory, `_zero` optional).
- Statuses: `statusLabel(t, 'booking', booking.status)` — never `t(status)` directly.
- Dynamic keys: build the key from a fixed internal value (`t(`status.booking.${status}`)`), never from display text.
- `ms` translations: author real Malay alongside zh; when unsure of a Malay term, mirror the structure of existing `ms/*.json` files. Never leave ms keys English — the parity test allows missing keys to fall back, but this plan keeps ms complete.

```rust
pub fn format_date(&self, date: chrono::NaiveDate) -> String {
    use chrono::Datelike;
    let month_key = format!("email.months.{:02}", date.month());
    let pattern = self.message("email.date.pattern");
    let pattern = if pattern == "email.date.pattern" {
        "{{day}} {{month}} {{year}}"
    } else {
        pattern
    };
    interpolate(
        pattern,
        &[
            ("day", &format!("{:02}", date.day())),
            ("day_num", &date.day().to_string()),
            ("month", self.message(&month_key)),
            ("year", &date.year().to_string()),
        ],
    )
}
```

### Task 7: `statusLabel` helper

**Files:**
- Create: `hotel-web-fe/src/i18n/statusLabel.ts`, `hotel-web-fe/src/i18n/statusLabel.test.ts`
- Modify: `hotel-web-fe/src/i18n/index.ts` (export)

```ts
import type { UseTranslationResult } from './useTranslation';

const humanize = (value: string): string =>
  value.replace(/[_-]+/g, ' ').replace(/\b\w/g, (c) => c.toUpperCase());

/** Localized display label for an internal status value. */
export const statusLabel = (
  t: UseTranslationResult['t'],
  domain: string,
  value: string | null | undefined
): string => {
  if (!value) return t('status:generic.unknown');
  const key = `${domain}.${value}`;
  const translated = t(`status:${key}`);
  // Engine renders the last segment (the raw value) on a missing key — for an
  // unmapped status, humanize beats leaking `checked_in` verbatim.
  return translated === value ? humanize(value) : translated;
};
```

Tests: known → localized; unknown → `"Checked In"`; null → generic unknown; zh locale → Chinese label. Then commit `feat(i18n): centralized status label helper`.

**Interfaces:** Produces `statusLabel(t, domain, value)` consumed by every wave that renders a status Chip/Badge.
