# DB Baseline + Staging Seed Consolidation Plan

**Goal:** two canonical commands — `make db-baseline` (schema + system bootstrap + patch catalog) and `make db-seed` (comprehensive deterministic staging dataset) — with one self-contained staging seed file, documented and verified clean-room.

**Architecture:** keep the existing V1 lifecycle (baseline → system seed → ordered patch catalog) untouched; add `database/postgres/staging.sql` as the single staging-data entry point, applied by a new `db-seed` Make target. No schema changes, no new tools, no new dependencies.

## Audit findings (constraints the design must respect)

- Engine: PostgreSQL 19 only (dev `postgres:19beta2` via `hotel-db` container on :5432; CI `19beta3`). No local `psql` binary — verify through `docker exec hotel-db psql` or a scratch DB inside it.
- Canonical install set is **pinned** by `tests/status_vocabulary.rs::postgres_initialization_has_baseline_seed_and_ordered_patches`: requires `migrations/0001_v1_baseline.sql`, `seed.sql`, `patches/`; forbids `data.sql`, `upgrade/`. A `staging.sql` file is permitted.
- `seed.sql` is system bootstrap only (roles, permissions, route policies, settings, channels, loyalty program, admin+superadmin, 4 room types, 16 rooms, 3 teams, welcome voucher). One-shot; RAISEs on re-run. This stays the "baseline" side.
- No staging/test dataset exists anywhere. `database/seed_voucher_audit.sql` is **untracked in-flight work from another session** (999xxx id band, dev-only) — do not touch.
- Identity columns are `GENERATED ALWAYS AS IDENTITY`; explicit-id inserts require `OVERRIDING SYSTEM VALUE`. Repo fixture convention (from seed_voucher_audit.sql): dedicated id band + band-scoped delete-first rerun.
- Trigger machinery the seed must respect:
  - `bookings_no_room_date_overlap` EXCLUDE — overlapping stays on one room in active statuses are DB-rejected (negative-test overlap scenarios are impossible to seed; they belong to API tests — document).
  - `trg_sync_room_status_booking` AFTER INSERT/UPDATE on bookings → `update_room_status()` → validates transition (auto-seeds `room_status_transitions`), writes `room_status_change_log` + `room_history`, auto-creates `housekeeping_tasks` for dirty outcomes. Past stays (check_out < CURRENT_DATE) are skipped.
  - `trg_sync_booking_payment_status` on payments → recomputes `bookings.payment_status` = void | paid | partial | unpaid from completed non-deposit non-refund payments vs `total_amount + tourism_tax_amount + extra_bed_charge`.
  - `trg_enforce_booking_tourism_tax` BEFORE INSERT → derives `is_tourist`/`tourism_tax_amount` from `guests.tourism_type='foreign'` × `system_settings.tourism_tax_rate` (10) × nights.
  - `trigger_validate_booking_occupancy` — adults+children ≤ room_types.max_occupancy (infants excluded).
  - `audit_logs` is append-only (mutation trigger) and monthly-partitioned; seed inserts need a marker guard instead of band-delete.
  - `customer_ledgers` folio/invoice numbers auto-generated by triggers — omit those columns.
- Status vocabularies (verbatim from CHECK constraints) are documented in staging.sql header comments.
- Booking channels (12) and loyalty program/tiers/rules already seeded by seed.sql — reuse, don't duplicate.
- No HR/payroll tables exist (no employees/salary/attendance/leave/payroll). Only teams/team_members/team_roles. Documented gap.
- `deploy.sh`/`deploy-staging.sh`/deploy workflows carry hardcoded per-patch file lists enforced by `tests/postgres_patch_catalog.rs`. Staging data is never deployed → no deploy changes.
- Desktop `sync:resources` copies only baseline + seed + manifest catalog → `staging.sql` is excluded by default (correct: never ship test data).
- Docs to update: `database/README.md` (owns DB lifecycle docs), `docs/DEVELOPMENT.md`, `CLAUDE.md` command list, `AGENTS.md` Postgres contract note.
- Staging env note: `deploy/docker-compose.staging.yml` runs `postgres:16` while the baseline is PG19-native — pre-existing platform gap, flag in audit summary; `db-seed` presumes a working V1 database regardless.

```text
├── migrations/0001_v1_baseline.sql   # unchanged
├── seed.sql                        # unchanged (system bootstrap)
├── patches/                        # unchanged
├── staging.sql                     # NEW — single staging entry point
└── ...
Makefile                            # + db-baseline, db-seed; db-setup → deprecated alias
hotel-app-be/database/README.md     # rewrite init docs around the two commands
docs/DEVELOPMENT.md                 # point at make db-baseline / db-seed
.github/workflows/ci.yml            # + staging-seed apply step in backend-pg job
CLAUDE.md / AGENTS.md               # one-line contract updates
```

Single file (not a `staging/` dir of parts): consistent with baseline/seed.sql convention, pipeable via stdin to `docker exec` and `psql -f` alike (no `\ir` fragility), and `status_vocabulary` test constraints stay trivially satisfied.

## staging.sql design

- `\set ON_ERROR_STOP on`, single `BEGIN…COMMIT`, advisory lock.
- Guard: abort unless `hotel_schema_revisions` has generation 1 version 1 (baseline ran first).
- Reference date: `COALESCE(current_setting('staging.ref_date', true)::date, CURRENT_DATE)` — default "today", overridable via `PGOPTIONS='-c staging.ref_date=YYYY-MM-DD'`. All stay dates derive from it → data never goes stale.
- **ID band 800000–899999** for every staging row (999xxx = dev-audit fixtures; runtime sequences start at 1 or 1000). uuid-keyed rows get fixed `80000000-…` uuids.
- Rerun = transaction: band-scoped DELETEs children→parents → re-INSERT `OVERRIDING SYSTEM VALUE` → `setval` each touched sequence past the band. audit_logs: `WHERE NOT EXISTS … details->>'staging_seed'` marker (append-only).
- No `random()`; amounts derived arithmetically (rate × nights, 8% service tax, RM10/night tourism tax for foreign guests — matching seeded settings).

Sections (FK order): 00 guard → 05 band cleanup → 10 users/access (manager, receptionist, housekeeping, finance/auditor, marketing, support_readonly, ekyc_reviewer, inactive + locked accounts, guest-portal user; user_roles, user_permissions, team_members) → 20 inventory (amenities, 2 extra room types, ~24 rooms incl. maintenance/out_of_order/reserved_dirty, room_type_amenities, rate_plans, room_rates, online_inventory_allocations) → 30 guests/CRM (~50 guests: members/non, foreign/local, VIP, blacklisted, corporate, incomplete, near-duplicates; companies, corporate_accounts+contacts, notes/preferences/documents/reviews, segments, user_guests, notification_subscriptions, consent_records) → 40 bookings (~70: bulk completed history via generate_series + explicit current/future matrix covering every status, multi-guest, same-day, multi-night, complimentary, OTA w/ commission, corporate bill, special requests; booking_guests, services catalog, booking_services, booking_history, booking_modifications, room_changes) → 50 finance (payments: full/partial/multi/deposit/failed/pending/refunded across all 7 methods; invoices all statuses; customer_ledgers + payments; vouchers/redemptions; receipt requests) → 60 ops (housekeeping tasks all statuses/priorities incl. overdue; maintenance tickets all statuses; night_audit_runs+details+posted_nights for ~30 days; job_runs; room_events) → 70 marketing (promotions across all 5 statuses, deal+voucher kinds; promotion_room_types/channels/loyalty_tiers; email_templates; email_campaigns all statuses; email_deliveries incl. failed/suppressed; email_suppressions; vouchers lifecycle) → 80 loyalty+portal (loyalty_members/accounts/transactions/redemptions, memberships, points_transactions, reward_catalog+redemptions, complimentary credits, guest_portal_sessions, self_checkin_events, staff_notifications+reads, marker-guarded audit_logs) → 90 setval + `RAISE NOTICE` count summary.

Edge cases embedded: occupancy = max_occupancy, 1-night and 30-night stays, zero-discount, large valid amount, long-name guest, minimal-profile guest, unpaid/overdue invoice, deposit-only, partial refund, fully refunded+voided, maintenance-blocked room, staff with no activity, unresolved complaint, overdue HK task, campaign with zero sends, empty band bookings for pagination/sort/filter.

## Verification (clean-room, in hotel-db container)

1. `CREATE DATABASE hotel_seed_verify` → `psql -f baseline` → `psql -f seed.sql` → `apply-patches.sh --container hotel-db …` → expect 1.1 + 1.2…1.23 revisions.
2. `psql -f staging.sql` → zero errors; verify: FK integrity (`pg_constraint` violations), per-table counts, payment invariant (Σcompleted ≤ total+tax; refunds ≤ paid), zero overlap violations, room-status coherence, `payment_status` trigger outcomes.
3. Re-run `staging.sql` → identical counts (idempotent).
4. `make db-schema-drift` staging vs baseline-only scratch → schema identical (data-only).
5. `cargo test --test status_vocabulary --test postgres_patch_catalog` pass (install-set + deploy-contract tests).
6. `cargo check --all-features` unaffected (no Rust changes).
7. Drop scratch DBs.

## Out of scope / non-goals

- No changes to baseline, seed.sql, patches, manifest, deploy scripts/workflows, desktop sync, `seed_voucher_audit.sql`.
- No HR/payroll schema (doesn't exist), no eKYC verification payloads (sensitive-data module; ekyc_reviewer *user* is seeded, verification records are not — documented).
- Staging data is never auto-deployed; `make db-seed` is manual/CI-verified.
