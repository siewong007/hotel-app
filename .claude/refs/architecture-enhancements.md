## Current state (verified)

- Desktop build pipeline is already cache-aware: `hotel-desktop/scripts/desktop-prepare.mjs:11-16` runs 4 steps (sync resources, build frontend, build backend sidecar, copy sidecar); `build-backend-sidecar.mjs:54-63` hashes backend `src/`, `Cargo.toml/.lock`, `build.rs`, toolchain file and skips the Cargo build if unchanged. `hotel-desktop/BUILD_SPEED.md:5-24` documents this.
- `build.rs` (`hotel-desktop/src-tauri/build.rs:53-70`) force-deletes stale `pgsql`/`database` resource dirs from the Cargo `target` output on every build to avoid stale bundling — a `panic!` if it can't (e.g., app still running and holding a lock).
- Embedded PostgreSQL under `src-tauri/pgsql/` is **44MB** (`du -sh` output) containing `bin/`, `lib/postgresql@18/`, `share/postgresql@18/`. It is gitignored at the root (`.gitignore:37`, `hotel-desktop/src-tauri/pgsql/`) — there is **no script in the repo that downloads or provisions it**; `grep -rln "pg_embed|download.*postgres|EMBEDDED_POSTGRES"` across `hotel-desktop/*.mjs|*.sh|*.md` returns nothing.
- Despite the binaries directory being gitignored (`.gitignore:38`, `hotel-desktop/src-tauri/binaries/`), a real ~16MB binary **is committed**: `git ls-files hotel-desktop/src-tauri/binaries` shows `hotel-app-be-aarch64-apple-darwin`, force-added, last touched 2026-06-19 (`git log`), 16,460,048 bytes (`git cat-file -s`).
- PostgreSQL lifecycle is handled in `hotel-desktop/src-tauri/src/postgres.rs`: `init_postgres_data_dir` (line 395) runs `initdb` with `scram-sha-256` auth and a randomly generated 32-byte password persisted to a `0600`-permission file (`write_postgres_password_file`, line 347-376); `start_postgres`/`stop_postgres` (lines 513, 662) shell out to `pg_ctl`; version compatibility is enforced by comparing the data dir's `PG_VERSION` against the bundled binary's detected major version and **refusing to start** on mismatch (`ensure_pgdata_version_compatible`, line 231; `IncompatibleDataDirectory` error, line 63-67) — no automatic `pg_upgrade` path exists, only manual recovery instructions in the error text.
- Backup is on-demand only: `commands::backup_database` (`commands.rs:301-311`) invokes `pg_dump` via `postgres::backup_database` (`postgres.rs:982`) into `<data_dir>/backups/`; there is no scheduled/automatic backup.
- Port discovery: the sidecar binds a dynamically-probed free port starting at `BACKEND_PORT` env or 3030 (`commands.rs:50-70, 101`), the webview learns it via a Tauri IPC `get_status` command / `backend-ready` event (`commands.rs:38-48, 185-187`) which the frontend consumes in `hotel-web-fe/src/desktop/runtimeApi.ts:194-203` and `DesktopServiceGate.tsx:67-141`.
- CORS in desktop mode: contrary to a broad "`ALLOWED_ORIGINS=*`" assumption, the sidecar is actually launched with a **specific origin allow-list**, not a wildcard: `commands.rs:113-116` sets `ALLOWED_ORIGINS` to `"tauri://localhost,http://tauri.localhost,http://localhost:3000,http://localhost:5173"`. The wildcard code path (`AllowedOrigins::Any` → `tower_http::cors::Any`, `hotel-app-be/src/routes/mod.rs:81-92`) exists in the backend but is not what desktop actually sets today.
- Updater is deliberately inert: `tauri.conf.json` has `"createUpdaterArtifacts": false` and literal placeholders `REPLACE_WITH_YOUR_UPDATE_HOST` / `REPLACE_WITH_TAURI_SIGNER_PUBLIC_KEY` (lines ~59-65); `hotel-desktop/UPDATER.md:1-5` confirms it is "wired in but not yet armed." Windows code signing is also unconfigured: `certificateThumbprint: null`, `timestampUrl: ""` (`tauri.conf.json`).
- Regular CI (`ci.yml` job `desktop`, `Desktop — Cargo Check`) still only stages `/dev/null` placeholders for the sidecar binary and pgsql resources and runs plain `cargo check`. A real `tauri build` now exists in `.github/workflows/desktop-build.yml` (added 2026-07; macOS-14 aarch64, workflow_dispatch + `v*` tags only — NOT per-PR), which provisions PostgreSQL from source via `POSTGRES_PREFIX` and runs `bun run build:no-bundle` / `bun run build`.
- The `sqlite` Cargo feature (`hotel-app-be/Cargo.toml:17`, `sqlite = ["sqlx/sqlite"]`) has **zero references anywhere under `hotel-desktop/`**: `grep -ril "sqlite" hotel-desktop --include='*.rs' --include='*.toml' --include='*.mjs' --include='*.json'` returns no matches. Desktop always uses the embedded PostgreSQL (`postgres.rs`), so SQLite is dead weight for this deployment target.
- Frontend/desktop duplicate build scripts: `hotel-web-fe/package.json` defines `start:tauri` (`vite --mode tauri --host 127.0.0.1 --strictPort`) and `build:tauri` (`vite build --mode tauri`), invoked from `hotel-desktop/scripts/build-frontend.mjs` (a caching wrapper that spawns `bun run build:tauri` in `hotel-web-fe/`) and from `tauri.conf.json`'s `beforeDevCommand`/`beforeBuildCommand` (both bun). The Vite dev proxy (`vite.config.ts:12-41`) is separately hand-maintained (`PROXY_PREFIXES`) from the desktop CORS allow-list in `commands.rs:114-116` — two independent lists of the same logical "trusted origins/routes" that must be kept in sync by hand.

## Enhancement opportunities

1. **Add a real desktop packaging job to CI (or a scheduled/manual workflow)** — DONE for macOS (2026-07): `.github/workflows/desktop-build.yml` runs `bun run build:no-bundle` (or full `bun run build` via input) on macos-14 aarch64, gated to `workflow_dispatch` + `v*` tags. Remaining gap: no Windows/Linux packaging job. Evidence: `.github/workflows/desktop-build.yml`; `BUILD_SPEED.md`. Effort remaining: M (Windows runner). Risk: low.

2. **Stop committing the built sidecar binary to git** — `hotel-desktop/src-tauri/binaries/hotel-app-be-aarch64-apple-darwin` is force-added despite being gitignored (16.4MB blob, `git ls-files` + `git cat-file -s` confirm), which bloats repo history irreversibly with every rebuild and risks committing a stale/mismatched-arch binary. Remove it from tracking (`git rm --cached`), rely on `desktop:prepare`/`copy-backend-sidecar.mjs` to regenerate it locally/in CI, and consider `git filter-repo` later to reclaim history size. Evidence: `git ls-files hotel-desktop/src-tauri/binaries`, `.gitignore:38`. Effort: S. Risk: low (verify no release process depends on the committed binary first).

3. **Remove the unused `sqlite` Cargo feature from desktop-relevant build paths, or document why it's kept** — `grep` across all of `hotel-desktop/` shows no reference to `sqlite`; the desktop app exclusively drives the bundled PostgreSQL (`postgres.rs`). Since CI already builds `--all-features` (`ci.yml` backend job) and a dedicated `backend-sqlite` job runs SQLite-only tests, the feature is clearly still used for something else (likely a lightweight/offline non-desktop SQLite mode), but its relationship to `hotel-desktop` should be documented or the feature flag pruned from any desktop build scripts if it's truly vestigial there. Evidence: grep above; `hotel-app-be/Cargo.toml:17`. Effort: S (investigation) / M (removal if confirmed dead). Risk: low.

4. **Automate embedded PostgreSQL provisioning** — There is no script to fetch/stage the 44MB `pgsql/` resource tree; it's gitignored and presumably placed by hand before `tauri build`, which is fragile (easy to build with a stale or wrong-platform pgsql, or forget to update it on a PostgreSQL version bump). Add a `scripts/fetch-pgsql.mjs` that downloads/verifies (checksum) the correct platform build of PostgreSQL 18 into `src-tauri/pgsql/`, wired into `desktop:prepare`, mirroring the existing `sync-desktop-resources.mjs` pattern. Evidence: `du -sh hotel-desktop/src-tauri/pgsql` = 44M; `.gitignore:37`; no matching fetch script found. Effort: M. Risk: low.

5. **Design and test a real PostgreSQL major-version upgrade path** — `ensure_pgdata_version_compatible` (`postgres.rs:231-248`) and `IncompatibleDataDirectory` (`postgres.rs:63-67`) only *detect* a version mismatch and refuse to start; there is no `pg_upgrade` automation, so any future bump of `CONFIGURED_POSTGRES_MAJOR_VERSION` (`postgres.rs:38`) from 18 to 19+ will strand every existing desktop install's data until a user manually runs `pg_upgrade` per the error message. Given this is a single-tenant embedded desktop DB, an in-app guided upgrade (dump via bundled `pg_dump` from the old binary set + restore into a fresh `initdb` on the new version, or ship both binary sets briefly) would remove a real data-loss risk. Evidence: `postgres.rs:63-67, 231-248`. Effort: L. Risk: med (data migration correctness).

6. **Wire up scheduled/automatic backups, not just on-demand `pg_dump`** — `backup_database` (`commands.rs:301-311`, `postgres.rs:982-1062`) is only invoked via an explicit Tauri command; there's no periodic backup, no retention/rotation policy for `<data_dir>/backups/`, and no backup-before-upgrade hook (which would also mitigate enhancement #5's risk). Add a simple interval timer (e.g., daily) plus retention pruning, triggered from `lib.rs`'s `setup()` alongside `start_services`. Evidence: `commands.rs:300-311`; `lib.rs:34-42` (only starts services, no backup scheduling). Effort: M. Risk: low.

7. **Arm or explicitly shelve the updater** — The updater plugin, capability, and IPC command are fully wired (`lib.rs:17-24`, `capabilities/default.json`) but non-functional: placeholder pubkey/endpoint and `createUpdaterArtifacts: false` (`tauri.conf.json`), confirmed inert by `UPDATER.md:1-5`. Half-wired auto-update is worse than none if a stale `check_for_updates` UI is exposed to users expecting it to work — either complete the 5 steps in `UPDATER.md` (signing key, endpoint, artifact generation, code signing) before next release, or hide the update-check UI until it is armed. Evidence: `tauri.conf.json` updater block; `UPDATER.md`. Effort: M (to arm) / S (to hide). Risk: low.

8. **Consolidate the two hand-maintained "trusted origin" lists** — The Vite dev proxy prefixes (`hotel-web-fe/vite.config.ts:12`, `PROXY_PREFIXES`) and the desktop sidecar's CORS allow-list (`hotel-desktop/src-tauri/src/commands.rs:114-116`) encode overlapping "what's a legitimate local origin/route" knowledge independently; a new route prefix or dev port added to one is easy to forget in the other. Extract a small shared constants module (or at minimum a code comment cross-referencing both locations) so the two lists can't silently drift, similar to how `CLAUDE.md` already flags the FE proxy list as hand-maintained. Evidence: `vite.config.ts:12,41`; `commands.rs:113-116`. Effort: S. Risk: low.
